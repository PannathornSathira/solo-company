# Phase 1 — Module 05 (P1-M05): Minimal LangGraph Runtime

## 1. Objective & Scope

Module `P1-M05` implements the GPT-owned backend runtime for the Phase 1
single-company MVP. It turns an objective into a structured, owner-approved
plan, executes approved specialist work sequentially, persists plain-language
events and Markdown artifacts, and finishes with a Chief of Staff executive
brief.

This module is backend-only. Server-Sent Events, retry and recovery hardening,
and the final error taxonomy remain in `P1-M06`; live frontend integration
remains in `P1-M07`.

## 2. Runtime Graph

```text
intake
  -> validate_objective
  -> create_plan
  -> wait_for_plan_approval
       -> revise -> create_plan
       -> approve -> execute_next_work_item
  -> persist_artifact
  -> repeat_until_complete
  -> synthesize_executive_brief
  -> complete
```

Unexpected model or persistence failures route to a terminal failure node.
Specialist work is strictly sequential and stops after the first failed item.

## 3. Persistence & Safety Rules

- A LangGraph checkpoint is written after each graph step. The database run ID
  is also the LangGraph `thread_id`.
- Checkpoint state contains JSON-safe identifiers, routing fields, revision
  feedback, and validated pending outputs. Database sessions, provider clients,
  prompts, credentials, and provider-native responses are never checkpointed.
- Runtime events use only the vocabulary accepted by ADR-002. Event payloads
  are validated and limited to 16 KiB before persistence.
- Prompt files are versioned. An agent's configured `prompt_version` must
  resolve exactly; the runtime never silently falls back to another prompt.
- The Chief of Staff may assign work only to enabled seeded specialist agents.
  It plans and synthesizes the brief but is not assigned specialist work.
- Approval requires an idempotency key. Reusing the same key returns the
  original run without repeating model calls or persistence effects.

## 4. Runtime Modes

- `fake` is the default and requires no paid API or credential. It produces a
  stable three-item plan and deterministic Markdown artifacts for tests.
- `gemini` is optional and uses the official Google GenAI SDK with Pydantic
  structured outputs. The Phase 1 alias `gemini-3.1-pro` maps to the configured
  provider model ID.
- PostgreSQL uses LangGraph's managed Postgres checkpoint tables. Tests use an
  in-memory checkpointer unless an opt-in PostgreSQL test is requested.

Configuration:

```text
RUNTIME_MODEL_BACKEND=fake
GRAPH_VERSION=p1-v1
GEMINI_API_KEY=
GEMINI_MODEL_ID=gemini-3.1-pro-preview
LANGGRAPH_DATABASE_URL=
RUN_REAL_MODEL_SMOKE=0
RUN_POSTGRES_CHECKPOINT_SMOKE=0
```

When `LANGGRAPH_DATABASE_URL` is empty, the runtime derives a Psycopg-compatible
URL from `DATABASE_URL`.

## 5. API Behavior

- `POST /api/objectives/{objective_id}/plan` creates a run, proposes two to five
  work items, and pauses for owner review.
- `POST /api/objectives/{objective_id}/plan/revise` records feedback, replaces
  only proposed work, and pauses on the revised plan.
- `POST /api/objectives/{objective_id}/plan/approve` claims the idempotency key
  and synchronously executes the approved run.
- `GET /api/runs/{run_id}`, `/events`, and `/artifacts` reload persisted runtime
  state. The SSE `/stream` route remains a `P1-M06` deliverable.

## 6. Verification

```bash
pnpm test
pnpm build
uv --directory apps/api run alembic upgrade head
```

The default suite uses the fake model and does not require PostgreSQL or Gemini.
Real-model and PostgreSQL checkpoint smoke tests are opt-in.

## 7. Handoff to P1-M06

`P1-M06` will integrate the runtime from a clean PostgreSQL database, implement
SSE resume behavior and retry semantics, harden concurrency and crash recovery,
and formalize the cross-endpoint error taxonomy.
