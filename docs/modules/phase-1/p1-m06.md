# Phase 1 — Module 06 (P1-M06): End-to-End Integration and Reliability

## 1. Objective and Owner

- Owner: GPT
- Objective: make the P1-M05 runtime immediately observable and safely
  recoverable by adding asynchronous in-process execution, resumable SSE,
  same-run retry, stable errors, replay idempotency, and clean-PostgreSQL
  integration coverage.

## 2. Scope

Allowed changes:

- Phase 1 API contracts, runtime orchestration, run repositories, migration,
  tests, generated TypeScript types, ADRs, roadmap, and operator/developer
  documentation.

Explicitly excluded:

- P1-M07 objective, plan, board, run, artifact, and SSE UI wiring;
- a separate worker deployable, queue, scheduler, backoff, cancellation, or
  multi-process execution;
- RAG, tools, additional providers, model selection, and Phase 2 behavior.

## 3. Approved Contracts

- `POST /api/objectives/{objective_id}/plan/approve` atomically claims approval,
  returns a `running` `AgentRun`, and schedules the run once.
- `GET /api/runs/{run_id}/stream` replays persisted events after the greater of
  `after_sequence` and `Last-Event-ID`. Frames use event sequence as `id`,
  event type as `event`, and the complete `RunEvent` JSON as `data`.
- `POST /api/runs/{run_id}/retry` returns `202`, keeps the run ID, and resumes
  only the failed work item or executive brief. Each attempt requires a new
  idempotency key.
- `AgentRun` exposes stable `RunErrorCode`, nullable `error_code`, and computed
  `retryable`.
- All JSON errors use `Error { code, message, details }` for `404`, `409`,
  `422`, `500`, `502`, and `503`.
- Retry uses the accepted `work.progress` event type; ADR-002's vocabulary is
  unchanged.

Database migration `0003_runtime_reliability` adds:

- append-only `run_retry_requests`, including `company_id`, retry target,
  optional failed work item, timestamps, and unique `(run_id,
  idempotency_key)`;
- a partial unique index allowing only one `pending`, `awaiting_approval`, or
  `running` run per company/objective.

Downgrade drops the retry table and active-run index. LangGraph checkpoint
tables remain managed by `PostgresSaver.setup()`, not Alembic.

## 4. Execution and Recovery Rules

- One in-process coordinator owns a single worker thread and deduplicates
  submitted run IDs.
- Approval and retry state is committed before submission. Startup scans
  `pending` and `running` runs and resumes from the persisted checkpoint.
- A persisted approval interrupt is released with an internal
  `approved_persisted` command. A terminal failed checkpoint jumps to the
  target stored in the latest retry request.
- Replayed nodes reuse running work and existing plans, artifacts, briefs, and
  terminal effects. Event sequence allocation locks the parent run.
- A hard crash may repeat a provider call after the provider responded but
  before checkpoint persistence. Events and artifacts must still occur once.
- SSE sends 15-second keep-alive comments, detects disconnects, and closes only
  after a completed or failed run's backlog is drained.

## 5. Acceptance and Verification

Default, credential-free acceptance:

```bash
pnpm test
pnpm build
```

Optional local PostgreSQL acceptance:

```bash
docker compose -f infra/compose.yaml up -d
RUN_POSTGRES_CHECKPOINT_SMOKE=1 \
  uv --directory apps/api run pytest -m postgres
```

The PostgreSQL suite creates a unique temporary schema, migrates from empty to
`head`, initializes PostgresSaver, completes a fake-model run, rebuilds the
runtime from its checkpoint, verifies failed-stage retry, downgrades the
application tables, and drops the schema.

The existing real-model smoke remains isolated:

```bash
RUN_REAL_MODEL_SMOKE=1 uv --directory apps/api run pytest -m real_model
```

## 6. Definition of Done

- Approval returns before model execution completes and never double-schedules
  one idempotency key.
- SSE replay, live delivery, cursor resume, keep-alive, disconnect, and terminal
  closure behavior are tested.
- Failed specialist work and failed brief synthesis retry under the same run ID
  without repeating completed work or artifacts.
- Startup recovery works after approval is committed but before checkpoint
  resumption.
- OpenAPI, runtime Pydantic contracts, and generated TypeScript types agree.
- Default tests require no PostgreSQL or model credential; PostgreSQL and
  Gemini remain explicit opt-ins.
- ADR-001, ADR-002, ADR-003, roadmap, README, and AGENTS.md describe the
  implemented boundaries.

## 7. Decisions Requiring a New ADR

- a separate or multi-process worker;
- queue leases, cancellation, scheduled work, automatic retry, or backoff;
- a new event type or changed event/artifact envelope;
- provider-side exactly-once model invocation;
- authentication or public deployment.

### Environment and Migration Changes

- Apply `0003_runtime_reliability` with
  `uv --directory apps/api run alembic upgrade head`.
- No new runtime environment variable or paid credential is required.
- Continue running one Uvicorn process for Phase 1.

### Known Limitations

- The in-process worker is restart-recoverable but not a multi-process durable
  queue.
- Graceful shutdown waits for the current worker call. A hard crash relies on
  checkpoint recovery.
- Provider calls are at-least-once across the response-before-checkpoint crash
  window; persisted effects are replay-idempotent.

## 9. Exact Handoff to P1-M07

P1-M07 consumes `apps/web/lib/api-types.ts` and the committed OpenAPI contract
without changing backend contracts. It should:

- submit approval, navigate immediately using the returned run ID, and render
  its initial `running` state;
- load the REST timeline, open EventSource with `after_sequence` equal to the
  last loaded sequence, and deduplicate by sequence;
- reopen the stream after a manual retry and preserve the existing timeline;
- show retry only when `AgentRun.retryable` is true and generate a new
  idempotency key per attempt;
- render stable error codes and owner-facing event summaries without claiming
  access to private reasoning.
